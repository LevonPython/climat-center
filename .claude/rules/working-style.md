# Working style

## Scope
- Address the explicit request. No tangents or unrequested refactors; report anything else you notice instead of changing it.
- Check claims against the code before relying on them, and challenge an assumption when the evidence contradicts it. Be blunt, concise and accurate.
- Give the simplest correct fix first. Offer a workaround only when the direct fix is impossible, and say why.
- Search for existing logic before writing new code (`client/lib/`, `admin/src/contentSchemas/utils.ts`, `server/src/middleware/`).

## Code
- Don't mutate inputs or globals; return new values.
- Validate input early and fail with a clear error.
- Keep it minimal: no duplicated logic, no speculative abstractions.
- In TypeScript, type props and exports explicitly and avoid `any` in new code.
- No comments by default. Keep one only for a non-obvious why, such as `// NOTE: Keep in sync with admin schema registry.`

## Attribution
Never attribute work to an AI tool: no `Co-Authored-By`, `Made-with`, `Generated by` or similar lines in commit messages, trailers, code comments, READMEs or PR descriptions.

## Git
- Commit subject: `type(scope): imperative summary`, 72 characters at most.
  - Types: `feat`, `fix`, `refactor`, `test`, `chore`, `docs`, `style`.
  - Scopes: `server`, `client`, `admin`, `e2e`, `i18n`, `content`, `db`, `deploy`.
- Branches: `feat/…`, `fix/…`, `chore/…`, cut from `main`.
- Stage explicit paths. Never stage `.env*` (except `.env.example`), build output or unrelated changes.
- Never use `--no-verify`. Never force-push `main`.
- Commit, push, merge or open issues only when asked.
